## 1. 总体节奏（四步）

1. 写功能伪代码 —— 先想清楚再敲语法。
2. 写代码实现 —— 对照伪代码，先把行为跑通。
3. 写优化伪代码 —— 在原步骤下加 1.1、1.2… 或单独一节，写清「要优化什么、改成什么样」。
4. 改代码做优化 —— 按 1.1 逐项落地，并做简单回归。

---

## 2. 伪代码怎么写

- 先写一句目标：这段程序解决什么问题（给人看，也给自己锚定范围）。**一个动宾短语写一个函数**，比如“读取文件”就可以写成一个函数`read_file()`.
- 写「做什么」多于「用什么 API」：例如「读成带换行的行列表」比死写 `read_text`（某个具体函数） 更稳；具体 API 实现时再定。
- 标清数据长什么样：关键变量是「路径 / 行列表 / 字符串 / 生成器」等，避免类型混用（例如 Path 直接当行序列）。
- 失败路径占一行：文件不存在、编码错误、空输入等，伪代码里点一下，实现时就不容易漏。
- 注释与代码同步：实现改了，顶部步骤或伪代码也改，避免「文档说 A、代码做 B」。

---

## 3. 第一版就要守住的底线（不必等「优化轮」）

- 编码、路径、环境：例如统一 `utf-8`、路径从哪来。
- 可观测：关键步骤能否从日志/输出判断成功或失败（生产尤其重要）。
- 敏感信息：密码、Token 不进日志、不进伪代码示例里的「真实值」。

---

## 4. 优化轮怎么写才有效

- 优化要带目标：性能 / 内存 / 可读性 / 可测试性 / 错误处理，写清「在满足什么前提下改什么」。
- 优化前心里有数：若涉及性能，至少知道瓶颈大概在哪（IO、算法、重复计算等）。
- 改完做回归：能跑测试就跑；没有测试就用固定样例（比如两份 `test_config_*.txt`）对一下输出是否还和预期一致。

---

## 5. 和协作、生产对齐的小习惯

- PR / 交接：必要时附上「意图 + 伪代码或步骤」，review 更快。
- 小函数：伪代码若已经是一大段，实现时拆成「读 / 比 / 输出」等小步，和伪代码层级对应，后面加 1.1 也好落点。

---

## 6. 一句话记住

先伪代码定意图与数据流 → 实现跑通 → 用带编号的优化伪代码约束改动 → 按目标优化并回归；伪代码写「做什么」和「数据形状」，底线不拖到优化轮。
