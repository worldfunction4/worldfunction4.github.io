# 多线程中线程的状态
## 准备销毁时的状态
首先需要使用`quit()`函数来让子线程退出事件循环，然后再使用`wait()`，这是主线程被调用的函数，会使主线程阻塞等待子线程回收，最后子线程触发`finished`信号发射，如果有槽函数就执行槽函数，比如`deleteLater()`。
### 如果不先`quit()`直接`wait()`呢？
那么这个时候由于`wait()`是被主线程调用，这时候它会使主线程进入阻塞等待子线程，而子线程内部的事件循环（也就是`exec()`）会一直等待新事件（造成**死锁**），两者谁都不会前进，就会导致程序**无期限挂起**。

## 因为多线程准备销毁时遇到的问题

### 没有运行事件循环要怎么让子线程停下来？
有时候子线程在执行一项耗时的纯CPU 计算任务（比如一个巨大的 `for` 循环），那么由于它没有运行事件循环，`quit()` 是无法让它停下来的。那么要怎么办呢？Qt 的中断机制可以解决这个问题。
- 发送中断请求：在主线程中，通过调用 `thread->requestInterruption()`，将线程内部的中断标志位置为 `true`

- 周期性检查：在子线程的计算循环内部，需要定期调用 `QThread::currentThread()->isInterruptionRequested()` 来主动检查这个标志位

- 进行退出：一旦检测到中断请求为真，工作类（Worker）应当立刻跳出循环（`break`），清理局部资源并正常结束函数，而不是粗暴地终止线程

不过...检查的频率要怎么平衡？每一次迭代都检查一次会带来较大的额外开销，频率低了会给用户带来视觉上的“卡顿”。我第一次想到：可以用执行的总次数除以期望的次数，也就是**取模**来控制检查；但要是数据是动态的呢？那么就是使用时间间隔显然更加合理了。

#### 如何利用时间间隔来检查上述提到的标志位呢？
配合 `QElapsedTimer` 可以非常优雅地实现这一点
例如，可以让代码每隔一定时间（如 50 毫秒）检查一次 `isInterruptionRequested()`，这样既保证了任务能被及时取消，又避免了过度查询带来的性能损耗

#### 如果子线程正在执行这种密集的纯 CPU 计算循环、且内部**没有**运行事件循环（没有调用 `exec()`）时，此时工作类（Worker）中的槽函数还能不能正常接收并响应外部发来的信号呢？
Qt当然也对这种情况进行了封装，也就是`QtConcurrent`模块

与需要手动管理的 `moveToThread` 不同，`QtConcurrent` 允许我们直接把一个普通的函数或 Lambda 表达式扔到后台线程池中去运行，省去了繁琐的底层模板代码：
- `QtConcurrent::run()`： 一键将耗时任务丢给后台线程池执行
- `QFuture`和`QFutureWatcher`：来监控任务的状态、获取返回值，并原生支持取消操作

也就是说：因为可以把任务扔到线程池中，那么用哪个线程都无所谓，只要能完成任务就行，那这个就非常适合**处理独立的、可并行化的短期任务，例如批量处理数据或图像**。但很明显也有局限：由于 `QtConcurrent` 运行的任务内部**没有事件循环**，它们无法像 `moveToThread` 那样持续接收来自其他对象的异步信号或长期维持运行状态。（未完）
