# MVC
## 尽量采用`View`而不是`Widget`
原因有以下：
###  性能原因

- **Widget 系列（如 `QTableWidget`）：数据和界面绑死**
    
    - `QTableWidget` 内部自己管理数据（每一个单元格都是一个 `QTableWidgetItem` 对象）。
        
    - 如果你有 **100 万行数据**，用 `QTableWidget` 就要在内存里瞬间创建 100 万个 `QTableWidgetItem` 对象。这会吃光内存，导致界面直接卡死、崩溃。
        
- **View 系列（如 `QTableView`）：真正的按需加载（虚拟化）**
    
    - `QTableView` 采用的是 **Model-View（模型/视图）** 架构。界面（View）和数据（Model）是完全分离的。
        
    - 不管你的 Model 里面有多少万条数据，View 永远只渲染**当前屏幕能看得见的那几十个单元格**。内存开销极小，滑动极其丝滑。

###  难以维护

- **Widget 系列：牵一发而动全身**
    
    - 因为数据直接塞在控件里，当业务变复杂（比如需要对表格数据进行排序、过滤、异步加载、多线程刷新、或者多个界面共享同一份数据）时，你会发现代码全写在 UI 类里。UI 逻辑和数据处理逻辑绞缠在一起，变成“面条代码”，后期极难维护。
        
- **View 系列：职责单一，结构清晰**
    
    - 采用经典的 **MVC/MVVM 思想**：
        
        - **Model（数据模型）**：只负责存数据、读写数据库、网络请求。
            
        - **View（视图）**：只负责长什么样、怎么渲染、怎么响应点击。
            
    - 如果业务变了，或者换个界面展示方式，只需要重写或替换 Model/View 即可，代码解耦度高，非常容易维护和扩展。

但也不是说就永远不使用`Widget`了，小工具，数据量少时更适用，简单高效。
