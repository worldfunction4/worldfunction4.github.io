# 条件变量

## 背景
<!-- more -->

首先我们需要知道什么是条件变量：它是C++11提供的另外一种用于等待的同步机制，能够阻塞一个或多个线程，直到收到另外一个线程发出的通知或超时时才会唤醒当前阻塞的线程，需要和[互斥量](../互斥锁.md)配合使用。

那么，为什么会需要这个呢？

在多线程的编程中，经常会遇到这种场景：
线程A需要等待某个条件满足（比如数据处理完毕），才能继续向下执行，而这个条件又需要线程B来改变。

没有条件变量：
```cpp
//线程A在后台进行轮询
while(!ready)
{
	//什么都不做，死循环来检查ready是否变成了ture
}
```
很明显这样会导致**极度浪费CPU资源**，A在没有任何休眠或挂起的情况下执行`while(!ready)`死循环，CPU的一个核心就会被此线程100%占用，不断进行无意义检查，不仅会导致电脑发热，还会挤占其他线程计算资源。

为了解决这种浪费，**条件变量（`std::condition_variable`）** 就出现了。

## 机制

- **等待（wait）**： 条件不满足，A不会死循环，而是释放锁并进入休眠状态，不占用CPU算力
- **通知（notify）**：当B改变了条件，B会发出一个信号，唤醒正在休眠的A继续工作
## 使用

和`std::mutex`与`std::unique_lock`配合
使用一个简单的[生产者-消费者模型](生产者-消费者模型.md)：
```cpp
std::mutex mtx;
std::condition_variable cv; //条件变量对象
bool ready = false; //标志位

//A：等待通知（消费者）
void workThread()
{
	std::unique_lock<std::mutex> lock(mtx);

	//wait自动释放lock，并将当前线程挂起休眠
	//收到notify唤醒，重新获取lock，并检查ready是否为true
	cv.wait(lock, [] {return ready; });
	std::cout << "满足条件\n";
	
}
//B：负责改变条件并通知(生产者)
void mainThread()
{
	//模拟数据准备过程
	std::this_thread::sleep_for(std::chrono::seconds(3));
	{//让ready = true
		std::lock_guard<std::mutex> lock(mtx);
		ready = true;
		std::cout << "数据准备完毕\n";
	}
	cv.notify_one(); //发送信号，唤醒在cv上等待的线程
}
```

在上面例子中有这么一行:
```cpp
cv.wait(lock, []{return ready;});
```
其中第二个参数是一个匿名函数，因为没有输入所以`()`可以不写，如果没有这个lambda表达式，直接调用`cv.wait()`呢？这会引发一个隐患：**虚假唤醒**。

## 虚假唤醒

简单来说，所谓虚假唤醒：线程没有收到通知（即没有谁调用`notfy`），但它自己却莫名其妙从`wait`状态醒过来了

### 发生原因

底层操作系统线程调度机制决定的。os为了性能和实现的效率，在某些极端情况（如中断，信号响应，上下文切换）下，允许处于等待状态的线程被提前唤醒。
所以：**永远不要假设线程醒来就一定是条件满足了**。

### 发生后造成后果
不加上Lambda表达式这样写：
```cpp
void workerThread() {
    std::unique_lock<std::mutex> lock(mtx);
    // 线程在这里休眠...
    cv.wait(lock); 
    // 如果发生了虚假唤醒：
    // ready 依然是 false，但线程直接醒来并继续向下执行了！
    // 此时访问未准备好的数据，就会导致崩溃或逻辑错误！
    std::cout << "开始处理数据..." << std::endl; 
}
```
为了防止这种意外，传统做法是在外面套一层`while`：
```cpp
while(!ready)
{
	cv.wait(lock);
}
```
所以这就是C++11提供的语法糖：
```cpp
cv.wait(lock, []{return ready;});
```
换句话说，标准库里的这个`wait`就是对传统做法进行的优化。

## `notfy_all()`的应用
和`notfy_one()`每次唤醒一个线程不同，`notfy_all()`会广播信号，唤醒所有正在该变量上休眠的线程。
### 广播通知（一对多通知）

当某个事情发生时，多个不同后台线程都需要同时知道这个消息并各自开始工作。
- 场景：游戏加载界面
- 应用：主线程负责解压资源文件。解压完成后，需要通知：
  - 线程1：渲染3D模型
  - 线程2：播放BGM
  - 线程3：初始化AI逻辑
- 做法：此时主线程修改标志位，调用`cv.notfy_all()`，这三个休眠的线程就会同时醒来并开始工作。

### 读写者模式（多个读者）

当数据发生更新后，**多个读取线程**可以同时并发地去读取数据。 
- 场景：配置数据更新
- 应用：如果配置项（例如系统参数）被修改了，后台有多个处理业务的“读者线程”都在等待最新的配置
- 做法：更新线程修改完配置后，调用 `notify_all()`。由于读取操作互相不冲突，所有被唤醒的“读者线程”都可以同时醒来读取最新的配置数据

### 多线程并行计算（同步屏障）

当我们需要**多个线程同时到达某个时间节点**，再一起开始下一阶段的计算时：
- 场景：**并行数据计算**（如大数组拆分计算）
- 应用：假设把一个巨型任务拆分给了 4 个线程，每个线程算完第一阶段后都在等待，只有当 4 个线程都算完第一阶段，才能一起进入第二阶段
- 做法：最后一个完成第一阶段的线程会调用 `notify_all()`，把前面 3 个停下来等待的线程全部唤醒，大家一起进入第二阶段
