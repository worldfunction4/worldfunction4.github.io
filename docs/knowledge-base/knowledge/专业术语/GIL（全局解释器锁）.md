## 什么是GIL？

翻译过来意思就是**全局解释器锁**，其实就是一个互斥锁。举个例子：如果把 Python 的解释器（[CPython](/knowledge-base/knowledge/Python/CPython.md)）想象成一间**高效率的办公室**，而线程是里面的**员工**，那么 **GIL（Global Interpreter Lock，全局解释器锁）** 就是这间办公室门上唯一的一把**钥匙**。

不管办公室里有多少个员工，**同一时刻只能有一个人拿着钥匙进去办公**。

## 为什么会有GIL？

GIL 并不是 Python 这种语言的特性，而是 **CPython** 为了解决**内存管理**问题而引入的一个机制。
### 核心原因：引用计数（Reference Counting）

Python 使用[引用计数](/knowledge-base/knowledge/Python/引用计数.md)的内存管理机制来进行管理。每当一个对象被引用，计数加 1；引用失效，计数减 1。当计数归零，对象就会被销毁。
- **问题**：如果有多个线程同时修改同一个对象的引用计数，可能会导致内存泄漏，或者更糟——对象还没用完就被销毁了（非法访问）。
- **解决方法**：为了保证计数的绝对安全，最简单粗暴的方法就是给整个解释器加一把大锁。谁要跑代码，谁就得先拿到这把锁。
## GIL运作逻辑

在多线程环境下，GIL 的工作流程大致如下：

1. **获取锁**：线程 A 抢到了 GIL，开始执行代码。
    
2. **执行代码**：线程 A 运行了一段时间（或者遇到了 I/O 操作），但并没停止。
    
3. **释放锁**：线程 A 释放 GIL。
    
4. **轮转**：操作系统唤醒其他等待的线程，大家开始新一轮的“抢钥匙”比赛。
    

> **重点**：在 **CPU 密集型**任务中，这种“抢钥匙”和“交钥匙”的过程会产生巨大的额外开销，而且因为同一时间只有一个线程在跑，多核 CPU 的优势完全发挥不出来。

## GIL带来的缺点
### CPU 密集型任务：影响大

假设一台电脑有 8 核 CPU，我们开了 8 个线程去计算圆周率：

- **理论上**：应该比单线程快 8 倍。
    
- **实际上**：这 8 个线程会为了争夺 GIL 锁打得不可开交，由于频繁的[上下文切换](/knowledge-base/knowledge/专业术语/上下文切换.md)，速度可能**比单线程还要慢**。
    

### I/O 密集型任务：几乎没影响

这是作为 [NetDevOps](/knowledge-base/knowledge/Python/NetDevOps.md) 最关心的部分。

- 当我们发起一个 SSH 连接或读取文件时，线程会进入等待状态。
    
- **关键点**：Python 的线程在等待 I/O 时，会**主动释放 GIL**。
    
- **结果**：线程 A 等网络返回时，线程 B 拿走钥匙开始工作。所以对于网络巡检脚本，多线程依然能带来近乎线性的性能提升。

## 如何绕过 GIL？

1.**使用多进程 (`multiprocessing`)**： 每个进程都有自己独立的解释器和独立的 GIL。既然一间办公室只有一把钥匙，那我们就多盖几间办公室，这大概是解决 Python 计算瓶颈的最佳方案。
    
2.**使用 C 扩展**： 如果我们用 Python 调用 NumPy 或 Pandas 等库，这些库的底层是用 C 语言写的。在执行重型计算时，它们会暂时脱离 Python 解释器的控制，释放 GIL，实现真正的并行。
    
3.**更换解释器**： 虽然大多数人都在用 CPython，但像 **Jython** (Java 版) 或 **IronPython** (.NET 版) 是没有 GIL 的。不过它们对第三方库的兼容性较差。

## Python 3.13 的“无锁”实验

**Python 3.13** 引入了一个实验性的功能，允许在安装时选择“禁用 GIL”（Free-threaded Python）。
虽然现在还处于早期阶段，且可能导致单线程性能下降，但这标志着 Python 社区正在努力拆掉这堵围了几十年的墙。

|**维度**|**GIL 的表现**|
|---|---|
|**本质**|CPython 的一种互斥锁，保证线程安全。|
|**优点**|设计简单，让单线程程序运行极快，且易于集成 C 扩展。|
|**缺点**|导致多线程无法利用多核 CPU 进行并行计算。|
|**对我们的影响**|写 **计算程序** 用多进程；写 **网络脚本** 用多线程/协程。|
